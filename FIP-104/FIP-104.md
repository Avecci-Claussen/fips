# FIP-104: Mining → Index Mining Compounding

```
  FIP: 104
  Title: Mining → Index Mining Compounding via Allowlisted Pools
  Author: TheLonelyBit, MrShiddy, Fractal Community Contributors
  Status: Draft
  Revision: Rev-2.1
  Type: Standard Proposal
  Created: 2026-07-17
  Updated: 2026-08-06
  Requires: FIP-101
  Layer: Staking system (non-consensus)
  Activation: Documentation + portal guidance + ≥1 live opt-in compound path
```

## Language

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## Abstract

This proposal defines an official **Mining → Index Mining compounding** path for Fractal miners under FIP-101.

After a miner completes a normal FIP-101 Binding to an indexer, an allowlisted mining pool MAY offer **opt-in** payout (or forward) of mining rewards to that miner’s **bound stake address**. Confirmed credits increase Index Mining stake weight under FIP-101’s existing balance model. The miner retains exclusive control of stake keys. Pools MUST NOT take custody of stake keys and MUST NOT silently redirect payouts.

This proposal does **not** change consensus, Indexer blocks, Taproot stake scripts, proofs, settlement delay, or the long-term **1:1:1** reward target. It standardizes staking-portal policy and pool integration only.

Compounding is optional. Miners who do not opt in continue ordinary pool payouts with no Index Mining interaction.

## Proposal Summary

- **Prerequisite:** a valid FIP-101 Binding to an indexer, producing a derived Taproot stake address `S`.
- **Compound:** after Binding, an allowlisted pool MAY, with explicit miner consent, pay or forward mining FB to `S`.
- **Weight:** `stake_weight = confirmed_balance(S)` (unchanged from FIP-101). No new stake inscription per credit.
- **Custody:** miners keep exit keys; pools execute payouts only.
- **Wallets:** stake-address discovery MUST be wallet-agnostic (pubkey + indexer derive). No single wallet brand is required by this FIP.
- **Activation:** documentation, portal compound guidance, Fractal-published pool allowlist, and at least one live opt-in compound path. No hard fork.

## Motivation

FIP-101 establishes indexing as a third infrastructure pillar alongside merged and permissionless mining, with a long-term **1:1:1** reward target and non-custodial Taproot staking.

Today, mining income and Index Mining stake are operationally separate: earn FB → wallet → manually restake. That friction is highest for pool miners, who already have a trusted payout rail but no official way to compound into Index Mining weight.

FIP-101 already treats post-Binding stake weight as the confirmed balance of the bound stake address. Ordinary confirmed credits increase weight without a new stake inscription. What is missing is an **official, opt-in integration** so mining pools can pay that address safely—without custody, silent redirection, or consensus change.

## Design Overview

1. **Reuse FIP-101, do not extend consensus.** Binding, proofs, settlement, claim, and unstake remain exactly as specified in FIP-101 and its reference implementations.
2. **Pool as payout rail, not stake custodian.** The pool’s only new job is optional redirect of mining rewards to `S` after explicit opt-in.
3. **Indexer choice stays with the miner.** A pool MAY also operate an indexer and recommend it, but MUST NOT silently Bind the miner or change the miner’s indexer after Binding.
4. **Wallet neutrality.** Binding and exit may use any client that correctly implements FIP-101. Compounding on a pool MUST accept a verified stake address without requiring a specific wallet product.
5. **Default remains ordinary mining.** Users who never Bind or never opt in are unaffected.

## Goals and Non-Goals

### Goals

- Official Mining → Index Mining compounding after Binding
- Opt-in pool pay-to-stake or forward-to-stake as the primary rail
- Preserve FIP-101 non-custodial exit (miner-signed unstake and claim)
- Wallet-agnostic stake-address discovery
- No consensus or node upgrade

### Non-Goals

- Changing Binding, indexer registration, proof, reward allocation, or settlement rules
- Making compound the default pool payout
- Pool custody of stake keys
- Pool selection of the miner’s indexer after Binding
- Requiring every pool to implement compound for activation
- Requiring a specific wallet brand (including UniSat) for compound enablement

## Protocol Basis (FIP-101, Unchanged)

1. **Binding.** A valid FIP-101 stake inscription (`fip101,1,stake,<indexer_id>`) with the correct actor tapscript prefix binds the miner to a derived Taproot stake address `S` for that indexer. The first non-`OP_RETURN` output MUST pay `S`.
2. **Derivation.**

   ```text
   S = DeriveStakeAddress(indexer_id, user_pubkey, address_type)
   ```

   Derivation MUST match the reference implementations in `stake-indexer` and `unstake-tool`. The `address_type` code is part of the leaf; incorrect type yields a different `S`.
3. **Weight.** After Binding, stake weight is the confirmed UTXO balance of `S`. Later credits do not require a new stake inscription.
4. **Exit.** Unstake and Index Mining claim remain miner-signed. Pools cannot spend `S`.
5. **Portal thresholds.** Any first-stake minimum enforced by official builders (historically discussed as 50 FB during testing) is **portal policy**, not consensus. This FIP does not depend on a specific minimum value.

## Specification

### 1. Definitions

| Term | Meaning |
| --- | --- |
| Stake address `S` | FIP-101 Taproot vault for `(indexer_id, user_pubkey, address_type)` |
| Binding | Valid first stake linking the miner to `S` for a given indexer |
| Compound | Opt-in pool payout or forward of mining FB to bound `S` |
| Allowlisted pool | Mining pool published by Fractal core as eligible for FIP-104 compound |
| Ordinary payout | Pool payment to the miner’s normal mining receipt address |

### 2. Default miner behavior

Unless the miner explicitly opts in to compound:

1. The pool MUST continue ordinary payouts to the miner’s configured payout address.
2. No Binding is required to mine.
3. No Index Mining interaction is implied by joining an allowlisted pool.

### 3. Compound miner flow

1. The miner completes a FIP-101 Binding to a chosen indexer and obtains stake address `S`.
2. On an allowlisted pool, the miner **explicitly opts in** to compound and confirms `S`.
3. While compound is enabled, the pool MUST pay mining rewards to `S`, or forward equivalent credits to `S` in reasonable chunks.
4. Confirmed credits increase `balance(S)` and therefore Index Mining weight.
5. The miner claims Index Mining rewards and unstakes using their own keys (FIP-101).

The pool MUST present `S` clearly before enablement and SHOULD warn that funds sent to `S` are stake principal until the miner unstakes.

### 4. Stake-address discovery

Official Fractal-sponsored tooling MUST support at least one of:

1. Wallet connect that reads address and pubkey, requires indexer selection, and displays `S`; or
2. A keyless derive helper that computes `S` from `indexer_id`, pubkey, and `address_type`.

Tools MUST NOT request seeds or private keys.

Pools MUST accept a miner-supplied `S` for compound enablement. Pools SHOULD verify that `S` matches a Binding known to `stake-indexer` (for example via `GET /users/:address/stakings`) or re-derive `S` with the same inputs the miner used for Binding.

**Forbidden**

- Deriving `S` from payout address alone
- Silently choosing or changing the miner’s indexer after Binding
- Requiring a specific wallet brand solely to enable pool compound

### 5. Pool allowlist and compound modes

1. Fractal core MUST publish a pool allowlist containing at least: `pool_id`, status, supported compound mode(s), and contact or status endpoint.
2. Core MAY add, suspend, or remove pools for abuse, false representation, or sustained non-compliance.
3. After Binding and explicit opt-in, an allowlisted pool MAY:
   - **Pay-to-stake:** set the miner’s reward address to bound `S`; or
   - **Forward-to-stake:** keep internal accounting on the ordinary address and periodically send confirmed FB to `S`.
4. Compound MUST NOT be a silent default.
5. Pools MUST NOT hold stake keys and MUST NOT build or broadcast unstake or claim transactions on the miner’s behalf.
6. A pool that also operates an indexer MAY recommend its `indexer_id` for Binding. Recommendation MUST remain explicit and revocable; it MUST NOT auto-Bind.

### 6. Unchanged

The following remain as in FIP-101 and its reference implementations:

- Indexer registration and proof submission
- Reward allocation and 1:1:1 long-term target
- Settlement delay
- Claim and unstake mechanics
- Stake scripts and consensus Indexer blocks

Nodes need no upgrade for this FIP. `fractal-indexer` statehash and proof-publisher operation are unchanged and are not required for ordinary credits to increase `balance(S)`.

## Worked Example

1. Alice Binds to indexer `1818297:10` and receives stake address `S`.
2. On allowlisted Pool P she enables compound and confirms `S`.
3. Pool P pays **3.2 FB** mining reward to `S` (ordinary payment; no new stake inscription).
4. `stake-indexer` updates weight from `confirmed_balance(S)`.
5. Alice later claims and unstakes with her keys. Pool P cannot spend `S`.
6. If Alice disables compound (or never enables it), Pool P pays her ordinary payout address as before.

## Security Considerations

| Risk | Mitigation |
| --- | --- |
| Pool steals stake principal | Impossible without miner key; `S` is the miner’s Taproot vault |
| Silent payout redirect | Compound MUST be explicit opt-in; default remains ordinary payout |
| Wrong `S` / address_type mismatch | Display and confirm `S`; prefer bound `S` from `stake-indexer`; open derive helper |
| Phishing / lookalike stake address | Confirm against portal or keyless derive before enablement |
| Pool selects indexer for miner | Forbidden after Binding; recommendation only with explicit consent |
| Credits before Binding | Funds sent to an unbound address are not Index Mining weight until Binding is recognized |
| Wallet lock-in | Compound enablement MUST NOT require a specific wallet brand |

**Trust boundary**

- Trust the pool for share accounting and payout execution.
- Do **not** trust the pool for custody, unstake, claim, or indexer choice.

## Compatibility

- Existing FIP-101 Bindings remain valid.
- No hard fork and no mandatory node upgrade.
- Miners and pools that ignore this FIP continue current behavior.
- Activation requires documentation, portal compound guidance, a published allowlist, and at least one live opt-in compound path.

## Execution Process

1. Confirm with Fractal core any portal first-stake threshold applicable at launch (value is non-normative for this FIP).
2. Publish allowlist schema and compound opt-in requirements for pools.
3. Ship portal guidance: Binding → display `S` → compound explanation; plus a keyless derive helper.
4. Onboard ≥1 allowlisted pool with live pay-to-stake or forward-to-stake.
5. Publish as a staking-system / documentation update (no flag day).

## Success Metrics (first 30 days after activation)

- FB volume paid to bound stake addresses via compound
- Unique addresses with compound enabled
- Share of allowlisted-pool hashrate operating in compound mode
